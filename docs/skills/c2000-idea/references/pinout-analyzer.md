# Pinout Analysis Workflow

Report every pin a C2000 F28x project uses on its device package. The workflow reads the
project's SysConfig configuration (when present) and its C sources, resolves every GPIO and
ADC channel to a physical package pin, and writes a pin report into the project.

It changes nothing in the project except writing `c2000-pinout.md`: no source edits, no
SysConfig `save`, no build-setting changes.

## When to use

The user asks which pins a project uses, wants a pin map or pin-usage table, asks which ADC
modules and channels are used, or wants to check the pins before a board layout, a package
change or a device migration. It covers:

- **Digital pins** — GPIO number, package pin, mux mode and signal, direction, pad
  configuration, input qualification, owning core, GPIO interrupts and input X-BAR use.
- **Analog pins** — ADC module and channel per pin, comparator (CMPSS) inputs, DAC outputs,
  PGA pins, analog mode on AGPIO pins, and ADC channels with no package pin.
- **System pins** — reset (XRSn), external clock (X1/X2), clock output (XCLKOUT), JTAG
  (TCK/TMS/TDI/TDO), the boot-mode select pins and the analog references (VREFHI/VREFLO).

## Required inputs

1. **Project** — the CCS project to analyze.

The device family and package are derived in Phase 1. Ask only for the package, and only when
the project has no `.syscfg` that states it.

## Dependencies

**idea-mcp** (required):
- `get_projects()` — the project's `currentDevice` family; it names the pinout file.

**ccs-project MCP** (required):
- `getProducts` — Phase 0 availability probe
- `getProjectDescriptors` — `location`, `device`, `activeBuildConfiguration`,
  `buildDirectoryLocation`, `sysConfigOutputLocation`
- `getProjectProductReferences` — C2000Ware location
- `getToolFlags` — compiler predefined symbols (select `device.h` branches)

**ccs-sysconfig MCP** (required when the project has a `.syscfg`):
- `listFiles` — Phase 0 availability probe
- `openFile` / `closeFile` — open and close the project's `.syscfg`
- `getModuleInstances` — configured module instances
- `getInstanceConfiguration` — ADC, CMPSS, DAC and PGA pin fields; clock-tree oscillator settings
- `getErrorsAndWarnings` — any error blocks the generated files
- `listGeneratedArtifacts` / `readGeneratedArtifact` — the generated `pinmux.csv`

Never call `save`, `changeConfiguration`, `addModuleInstances` or `removeModuleInstances`.

**ti-asm-mcp** (recommended):
- `list_devices` — Phase 0 availability probe
- `search_trm_keywords` — default boot-mode select pins for the device

## Data sources

| Source | Path | Gives |
|---|---|---|
| Pinout file | `references/pinout/pinout-md/<family>_<package>.md` | Every package pin: number or ball, name (analog functions, GPIO, system), mux columns 0–15 |
| Pin map header | `<c2000ware_path>/driverlib/<family>/driverlib/pin_map.h` | `GPIO_<n>_<SIGNAL>` macros; the low byte of each value is the mux mode |
| Device header | `<c2000ware_path>/device_support/<family>/common/include/device.h` | `DEVICE_GPIO_PIN_*` / `DEVICE_GPIO_CFG_*` board macros, per board `#ifdef` |
| SysConfig `pinmux.csv` | generated by SysConfig; also in `sysConfigOutputLocation` after a build | Every package pin with `Selected Mode` and `Used By` |

The pinout file path is relative to the `c2000-idea` skill folder. `<family>` and `<package>`
are lowercase in its name (e.g. `f28p55x_100pz.md`).

## Pin report file

The report lives in **the project directory**: `c2000-pinout.md`. Phase 1 creates it; each
phase appends its section; Phase 5 adds the final pin tables. Never overwrite an earlier
phase's section.

**If your context is getting long or you feel disoriented, re-read `c2000-pinout.md` to recover
your position.**

## Resuming

> STOP: **If `c2000-pinout.md` already exists in the project directory:** read it first.
> Continue from the first phase not recorded as COMPLETE. Do not repeat completed phases.

## How to run this workflow

> STOP: **Do not read ahead.** Read one phase file at a time. Complete every step in it.
> Return here. Only then read the next phase file.

**If any MCP tool call fails, returns an unexpected error, or produces a result you cannot
interpret — stop and ask the user.** Do not guess, retry blindly, or skip the step.

Phase 1 ends with a confirmation gate: the device family and package decide every pin number,
so wait for the user to confirm them. Phases 2–4 present their summary and continue. Phase 5
presents the report.

### Phase sequence

0. **Read `pinout-analyzer/phase-0-preflight.md`** — probe the MCP servers.
   → When complete, return here.

1. **Read `pinout-analyzer/phase-1-device-package.md`** — identify the project, device family,
   package, pinout file and predefined symbols; create `c2000-pinout.md`.
   → When complete, return here.

2. **Read `pinout-analyzer/phase-2-sysconfig-pins.md`** — pins configured in the `.syscfg`.
   Skip when the project has no `.syscfg`.
   → When complete, return here.

3. **Read `pinout-analyzer/phase-3-code-pins.md`** — pins configured or used in the C sources.
   → When complete, return here.

4. **Read `pinout-analyzer/phase-4-system-pins.md`** — reset, clock, JTAG, boot-mode and
   analog-reference pins.
   → When complete, return here.

5. **Read `pinout-analyzer/phase-5-report.md`** — merge, check and present the pin report.
   → Analysis complete.

## Do / Don't

- Do take pin numbers from the pinout file or SysConfig — never from memory or a datasheet
  recalled from training.
- Do take mux modes from the `pin_map.h` macro value, and signal names from the pinout file.
- Do resolve every macro and variable that carries a pin before recording it; record what
  cannot be resolved as `UNRESOLVED`, never as a guess.
- Do report pins per package — a GPIO the package does not bond out is a finding, not a pin.
- Don't change any project file, build setting or SysConfig setting. The only file written is
  `c2000-pinout.md`.
- Don't call SysConfig `save`, `changeConfiguration`, `addModuleInstances` or
  `removeModuleInstances`.
